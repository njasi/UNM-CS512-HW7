      Structure

      There were a couple of interesting structural decisions I made while working on this pipeline, notably how the javascript in our scene manager communicates the objects, lights, and materials to the shaders. For all three of these we use a buffer region to pass information to the shader.

      During this process I also learned that within a uniform block (std140) vec3s are actually padded to use the same stride as a vec4. That is, a vec3 will take up 16 bytes (enough for a vec4!) of space rather than 12 bytes you might assume it would use with 32 bit precision. This is why my structs use vec4 types rather than vec3... I'm not willing to lose those extra bytes to padding!

      Additionally, this padding extends to the mat3 type which essentially uses three padded vec3s, wasting 12 whole bytes of space... However, I do currently use a mat3 within my ObjectTransformCache struct for simplicity's sake. We will talk about the struct's purpose in the optimization section, although I'm sure you can make a guess about it.

      Objects and Lights

      Currently objects and lights use the same struct, but different buffer blocks. This may change later to allow spotlights and directional lights, but we proceed with the simpile object based lights provided in the initial HW7 source for now. 

      const int OBJECT_TYPE_SPHERE = 0;

// all encompassing object layout passed from js.
struct Object {
  ivec4 meta;         // x    => type;    y => material; z=> cyl: faceted; w => cyl: faces (prism); 
  vec4 centerRadius;  // xyz  => center;  w => cone, sphere, cyl: r, cube: half-size, torus: R, plane: width
  vec4 options;       // x    => cyl, cone: height, torus:r, plane:depth;     y=> cyl: bulge,   w => light: power;
  vec4 testCenterRadius; // center of the object transformed into world space so we can check rays against it rather than needing to always transform into object space

};

      Textures

      The handling of textures is not very interesting, but it is worth noting before we cover materials. When you're working with textures in webgl you bind texture information to bind points and then your shader can read the information in the texture by using a sampler at that bind point. However, there is a limited number of bind points available, and it varies by machine. We are only guaranteed 16 binding points, which happens to be how many my laptop can use.

      This wouldn't be a problem in our previous mesh based pipeline, since we draw each object one at a time allowing them to all have their own set of 16 textures if you rebind before a draw call. You can easily use 2d textures here and have plenty of space to work with.

      However, in the ray tracer structure we are using, the entire scene is generated at once meaning you only get to have 16 textures for your scene if you use regular 2D textures. There are a couple ways around this including using a texture atlas where multiple textures are stored side by side in a single 2D texture, but I ended up using a 3D texture with many different layers, each of which is a 2D texture. webgl even has a TEXTURE_2D_ARRAY type that you can sample with the sampler2DArray. This works the same as a 2D texture, just that you also specify the layer or index of the 2D texture you want to sample. Overall this allows us many textures within a single bind point.

      Materials

      Materials communicated from our javascript controller work in much the same way as the objects and light above. We define a material struct and then a block of the structs we can use to pass information around. Although I had a couple of things in mind when making this structure.

      • We should be able to use textures in the ray tracer.
      • We should be able to define material properties procedurally.
      • Materials should be able to have layers of procedural or image textures (I used 6 layers in my HW6).
      • The material structure should stay small so we can define many of them in a single block.

      struct Material {
  vec4 ka; // w unused (xyz => ambient color of normal mat, light color, glass color, reflective color)
  vec4 kd; // w unused
  vec4 ks; // w unused 
  vec4 optics; // specular, refractiveIndex, reflectivity
  uvec4 textures; // see below section (why this struct is defined early)
};

      After some consideration this lead to the above Material struct. It resembles a basic phong material with some optics information tacked on, and the interesting (or overkill depending on how you look at it) part is in the last member which identifies the layers of textures in the material.

      Texture Descriptors

      Since I wanted at least 6 layers of textures which could be either sampled from our TEXTURE_2D_ARRAY or procedurally generated, allow these textures to be of different types (ie albedo, normal, bump etc), blend layers together in different ways (lighten, multiply, normal, etc), and be able to reference a fair amount of textures, we ended up with a fairly interesting descriptor layout. 

      // texture descriptor layout
//  a: 1 bit, b: 3: bits, c: 4 bits, d: 8 bits 
//  a: is 1 bit => function / texture
//  b: blend mode (3 bit => 8 options)  additive, max, multiply etc
//  c: texture / function type (4 bit => 16 options)  albedo, normal, bump, displacement, specular, optical maps...
//  d: texture / function num (8 bit => 256 options)
// 
// iiii iiii xxxx bbb f
// 1111 1111 1000 100 1
// const uint missingTextureDescriptor = 0b1111111110001001;

// pack information into a descriptor
uint packTexDescriptor(
  uint sourceType,
  uint blendMode,
  uint textureType,
  uint textureIndex
) {
  return (sourceType & 1u) |
    ((blendMode & 7u) << 1u) |
    ((textureType & 15u) << 4u) |
    ((textureIndex & 255u) << 8u);
}

      This descriptor layout takes up 16 bits, so with 32 bit precision we can store 8 different texture descriptors in a single uvec4. Of course this was completely unnecessary, but it was an interesting exercise, and allows us to have a minimum of 204 materials in a scene with a single material block so I'm happy with it.

      When calculating Material information we unpack all this information with bit shifts and masking and then act on it. For example if we see that the first bit represents a function then we look up the function and run it rather than sampling from a texture. Above you can see this in action with the missingTextureDescriptor which says to use function 255 as a albedo layer and blend it as a normal layer (ie replace what is below it).

      A texture descriptor is labeled as disabled by setting the blend mode to 0. Since webgl blocks are filled with 0s by default this allows us to not worry about materials without textures doing weird things. Although it is better to explicitly pack the 0 value in there, this is good enough for now.

      Procedural Textures

      Now let us consider procedural textures by reimplementing the black and white tiles provided on the infinite plane in the initial HW7 skeleton. After implementing uv coordinate calculations for our surfaces this is essentially a procedural texture. Give a function the uv coordinates and we can determine if we are in a black or white tile. 

      // checkerboard texture pattern based on the provided plane pattern
vec4 checkerTexture(vec2 uv, vec4 colorA, vec4 colorB, float scale) {
  ivec2 cell = ivec2(floor(uv * scale));
  bool checker = ((cell.x + cell.y) % 2) == 0;
  return checker ? colorA : colorB;
}

// our black and white tile texture
vec4 blackWhiteTiles(vec2 uv) {
  return checkerTexture(uv, vec4(0.f, 0.f, 0.f, 1.0f), vec4(1.0f), 2.f);
}

      Transmittance

      In the starter code provided to us we use a shadow ray casting model which works by casting a ray from an object towards a light in the scene. To get light to pass through glass and become tinted you need to implement a form of transmittance which is essentially how the color of light is effected by moving through a material. This should include reflection and refraction in a complete model, but this usually falls to path tracing as it is easiest to trace from the light source to the end light position rather than backwards in our model. I've implemented a couple modes of "transmittance" that "work" by altering our shadow tracing model slightly.

      The simple glass mode produces pretty reasonable results, but the TIR mode is notably lacking... Overall I prefer the fast glass mode which just shoots the rays straight through the glass tinting as it goes.

      Object Transformation

      One way to transform an object in a ray traced scene is to transform the incoming ray from world space to the local object space. Note that the transformation needed here is the same as needed for hierarchical modeling, you can kind of think of it like the ray becoming a child of the object.

      Unfortunately while simple, this means in a naive implementation we need to transform every ray into the space of every object which is the multiplication of the inverse of the object's transformation matrix and the ray. The resulting normal from the intersection also has to be transformed from object space back into world space so we can use it while rendering in terms of the world. This becomes especially costly when you need to sample multiple times per pixel.

      Caching The Transformations

      One simple way to alleviate this issue is to compute both transformations for each object instead of computing them at runtime. This could be done in the fragment shader, but we would still need to calculate the values once per fragment, while the matrices won't vary between fragments in a single frame. To calculate them once per frame we can calculate them on the CPU and use a buffer to pass them to the shader. 

      // we want to avoid calculating the inverse for every single ray as
// this won't change within a pass, so we can calculate it once at 
// the start of each pass on the cpu

struct ObjectTransformCache {
  mat4 invTransform;
  mat3 invNormalTransform;
};

layout(std140) uniform objectTransformBlock {
  ObjectTransformCache objTransformCache[MAX_OBJECTS];
};

layout(std140) uniform lightTransformBlock {
  ObjectTransformCache lightTransformCache[MAX_LIGHTS];
};

      Now we do not need to compute these transformations every time, this gave a significant boost to my initial basic implementation (1 fps back to ~10 fps at two bounces). However, we still have to transform a ray into the space of an object to test intersection between the two even if they are not anywhere close to intersecting.

      Cache Passing

      This is not really worth mentioning, but the performance difference was quite amusing to me. In my initial implementation I simply passed the entire ObjectTransformCache along with the object, however this tanked the performance. In the previous section we note jumping to 10 fps, but when passing the entire struct the jump was actually only 3 fps. This made me question everything and I changed it so we simply pass around the object's index and look up the cache as we need it. Usually this isnt an issue, because most languages have some sort of pointer setup allowing us to pass a couple bytes for an object of any size.

      Rough Intersection Test

      One common way to make intersections cheaper is by first doing a test intersection with a simple object such as a sphere which inscribes the actual target. This way we can test against a sphere rather than a potentially expensive target, and in our case we can even avoid transforming the ray into object space to check against our test sphere. 

      // all encompassing object layout passed from js.
struct Object {
  ivec4 meta;         
  vec4 centerRadius; 
  vec4 options;      
  // center of the object transformed into world space so we 
  // can check rays against it rather than needing to always 
  // transform into object space 
  vec4 testCenterRadius; .xyz => center, .w => radius
};

      You may have noticed an extra field earlier in the Object struct testCenterRadius. We calculate this in on the CPU in JS by applying the object's transformation against the center point. Since the this test center point has the transformation applied it will be at the true center of the object, but already in world space! The radius of the bounding sphere is calculated differently for every target primitive to ensure it inscribes the object. 

      // check against cheap sphere before doing expensive ray transforms
Sphere test = Sphere(obj.testCenterRadius.xyz, obj.testCenterRadius.w);
float testT;
if(!intersectSphere(test, worldRay, testT)) {
  return false;
}

      This was a huge performance saver, bumping me all the way back up to 30fps at 2 ray bounces. Unfortunately, if we get close to an object all rays have to be converted into its object space and we drop back down to 10 fps.

      Translation Only Flag

      When you scale, rotate or shear an object it is clear that we need to transform the ray to check intersection against the object. However, translation (and mirroring in some cases) does not alter the shape of the object, it simply shifts the centerpoint. Therefore we can avoid transforming the ray and check for object intersection using the test center point from the previous optimization as the real center of the object as it already has the translation applied. 

      // check against cheap sphere before doing expensive ray transforms
Sphere test = Sphere(obj.testCenterRadius.xyz, obj.testCenterRadius.w);
float testT;
if(obj.meta.w != OBJECT_TRANSFORM_TRANSLATE_ONLY && !intersectSphere(test, worldRay, testT)) {
  return false;
}

// transform ray to local object space...
Ray localRay;
vec3 center;

// if we have only performed translation then we can just use the 
// precalculated test point
// note that we can avoid the above intersect as well
if(obj.meta.w == OBJECT_TRANSFORM_TRANSLATE_ONLY) {
  center = obj.testCenterRadius.xyz;
  localRay = worldRay;
} else {
  center = obj.centerRadius.xyz;
  localRay = toObjectSpace(worldRay, otc, light);
}

      This translation only flag helps a lot, especially with an infinite ground plane.

      Notice that we can get an additional (small) savings since there is no need to use the test sphere above, since it's main purpose is to avoid ray transformation. Although some intersections are more expensive (notably my torus intersection) and it is useful to have a bounding sphere check on them anyway.
